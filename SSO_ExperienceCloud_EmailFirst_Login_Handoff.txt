SSO + EMAIL‑FIRST LOGIN FOR EXPERIENCE CLOUD (AURA NOW, LWR SOON)
Handoff for Cursor / Coding Agent

Owner / Context
- Salesforce org hosts a multi‑organization (multi‑client) Experience Cloud portal. Multiple client companies (partner users) access one shared site.
- Today: all client users authenticate with Salesforce username + password + MFA.
- New requirement: at least one client (example: “Peco Foods”) wants SSO via their Duo SSO IdP (SAML). Additional clients may follow.
- Goal: a maintainable routing solution where users enter an identifier (email) and are automatically routed to the correct pathway:
  - If user belongs to a client with SSO enabled: redirect into that client’s SAML configuration.
  - Otherwise: prompt for password and authenticate normally.

Key Goal
- Build a durable, “email first” login experience that works across BOTH Aura and LWR Experience Cloud sites.
- Avoid revisiting Apex code whenever a new client SSO connection is added.

High‑Level Design Criteria
1) Email‑first UX
   - First screen: single email input.
   - Second step: either (a) redirect to SSO, or (b) show password field.

2) Multi‑client SSO routing (metadata‑driven)
   - Use Permission Sets as “markers” on users (no actual permissions required).
   - Use Custom Metadata Type (CMDT) to map Permission Set Name -> SAML Setting (or Auth Provider) key.
   - Routing logic must be generic: adding new SSO clients should require only:
     - Create SAML setting
     - Create permission set
     - Add CMDT mapping record
     - Assign permission set to users
     - NO Apex code changes.

3) Durable across Aura + LWR
   - Avoid Visualforce login dependencies (LWR can constrain VF login page choices and switching between login page types can be limiting).
   - Prefer Experience Builder Login Page + LWC for login UX.

4) Privacy/Security
   - Do not log sensitive data (passwords, full session ids, full tokens).
   - Acceptable to log correlation IDs and high‑level routing decisions.

5) Reliability
   - Must not rely on Salesforce internal /_ui identity verification pages for the password step (see “What we learned”).


What We Tried (Experimentation Summary)
A) Experience Cloud “Login Discovery Page” + autogenerated Auth.LoginDiscoveryHandler
- Auto‑generated handler attempted to query TwoFactorMethodsInfo and use OTP/verification methods.
- In this org/sandbox, querying TwoFactorMethodsInfo failed with:
  - System.QueryException: sObject type ‘TwoFactorMethodsInfo’ is not supported. citeturn9search1
- We removed OTP/verification checks and tried to use password verification only.

B) Email‑first handler using Site.passwordlessLogin(..., PASSWORD, startUrl)
- Handler correctly found user by email and returned PageReference redirect URLs. citeturn12search1turn18search1turn21search1
- We discovered inbound startUrl values were often unsafe (e.g., /apex/CommunitiesLanding). citeturn18search1turn21search1
- We implemented startUrl normalization and forced the post-login return to /s/. citeturn21search1
- Despite forcing retURL=/s/, the browser still ended up back at /login with startURL pointing to an internal identity verification UI.

C) Root cause of the persistent loop
- After “failure,” the browser URL was:
  - /login?...&startURL=/_ui/identity/verification/method/PasswordVerificationUi/... (very long) 
  - This indicates Salesforce was attempting to route the password step through PasswordVerificationUi (internal identity verification UI) and was bouncing back to /login. (Observed directly in the failure URL provided by Louis.)
- The handler logs show Salesforce returning frontdoor.jsp links with retURL=/s/ (so the handler was returning a seemingly valid redirect). citeturn21search1
- Net: using Site.passwordlessLogin with VerificationMethod.PASSWORD is not reliably producing an accessible password entry step in this Experience Cloud context—likely because the platform attempts to use internal /_ui verification flows that loop back to /login.

Key working assumption based on evidence
- The internal identity verification password UI (/ _ui / identity / verification / method / PasswordVerificationUi) does not resolve/complete properly in this Experience Cloud setup, causing a hard loop back to the email prompt.


Recommended Durable Solution (Aura now + LWR later)
Implement a custom login UX using Experience Builder login page + LWC (no Visualforce), with Apex services to:
1) Discover user by email and decide routing:
   - If user has an SSO marker permission set and CMDT maps it -> SAML setting/auth provider, return “SSO” directive + redirect URL.
   - Else return “PASSWORD” directive.

2) Perform password auth without relying on PasswordVerificationUi:
   - Use Site.login(usernameOrEmail, password, startUrl) from Apex to authenticate and return a PageReference/URL.
   - (This avoids Site.passwordlessLogin(PASSWORD) which triggers PasswordVerificationUi loops.)

Implementation Components
A) Experience Builder Login Page
- Set Workspaces → Login & Registration → Login Page Type = Experience Builder Page.
- Place custom LWC on login page.

B) LWC: Email‑first login component
UI states:
- Step 1: Email input + “Next”
  - Calls Apex discover(email, startUrl)
  - If response.type == 'SSO': browser redirect to response.redirectUrl
  - If response.type == 'PASSWORD': advance to step 2
- Step 2: Password input + “Sign in”
  - Calls Apex passwordLogin(email, password, startUrl)
  - On success: window.location = returnedUrl
  - On failure: show friendly error (do not reveal whether email exists)

C) Apex: LoginRouterService (Apex class)
Suggested methods:
- @AuraEnabled(cacheable=false) static DiscoverResult discover(String email, String startUrl)
  - Normalize email.
  - Lookup active User by Email.
  - Determine eligible site membership if needed (optional; can rely on Site.login to fail).
  - Determine SSO mapping:
    - Query PermissionSetAssignment for user -> permission set names.
    - Query CMDT records with Permission_Set_Name__c IN (...) AND Is_Active__c = true
    - Pick highest priority if multiple.
  - If mapping found: build SAML initiation URL (details depend on SAML config; keep generic via CMDT).
  - Else: return PASSWORD.
  - Return normalized startUrl (force /s/).

- @AuraEnabled(cacheable=false) static LoginResult passwordLogin(String email, String password, String startUrl)
  - Normalize startUrl to /s/.
  - Attempt Site.login(usernameOrEmail, password, startUrl)
  - If null: return error
  - If PageReference: return URL string.

D) CMDT Design
Custom Metadata Type example: Client_Sso_Routing__mdt
Fields:
- Permission_Set_Name__c (Text, required): e.g., 'SSO__Client__Peco_Foods'
- Protocol__c (Picklist/Text): 'SAML' (future: 'OIDC')
- Sso_Config_Key__c (Text): API name of SAML setting or auth provider key
- Is_Active__c (Checkbox)
- Priority__c (Number)

E) Permission Set “Markers”
- One permission set per SSO client.
- No permissions required; purely a marker.

Logging / Debugging Approach (for new implementation)
- Louis does NOT want to carry forward the heavy debug instrumentation.
- Recommended lightweight approach:
  - Generate a correlationId per request.
  - Log only:
    - correlationId
    - email hash or masked email (e.g., a***@domain)
    - chosen route: SSO vs PASSWORD
    - mapped SSO key (not secrets)
  - No logging of passwords, session ids, full redirect URLs.

Known Constraints / Gotchas Learned
1) TwoFactorMethodsInfo sObject not supported in this org/sandbox context.
   - Any generated template code that queries TwoFactorMethodsInfo will fail. citeturn9search1

2) Login Discovery + password verification UI loop
   - In this environment, using Site.passwordlessLogin with PASSWORD leads to redirect chains that end up back at /login with startURL pointing to PasswordVerificationUi (internal identity verification UI), preventing the password entry UI from appearing.
   - Even when startUrl was forced to /s/ and retURL became /s/, the browser still landed on /login?...startURL=/_ui/identity/verification/method/PasswordVerificationUi... (observed directly).

3) startUrl values can be unsafe
   - Salesforce sometimes supplies startUrl like /apex/CommunitiesLanding during login flows. citeturn18search1turn21search1
   - For reliability, normalize/force to /s/.

4) Experience Cloud sessions/cookies
   - Session behavior is domain-scoped and redirects can replace cookies; authentication flows can be sensitive to cookie/session state across redirects. (Keep testing in incognito during development).

Acceptance Criteria
- External user enters email on login page.
- If user is assigned an SSO marker permission set with active CMDT mapping:
  - User is redirected to the correct IdP (SAML setting for that client).
- Otherwise:
  - User is shown a password field (in the custom LWC UI) and can sign in.
  - Successful login lands on https://pinionglobal--devpro1.sandbox.my.site.com/s/
- Adding a new SSO client requires only metadata + permission set assignments, no code.
